# Changelog

Notable changes to DSH Mobile are recorded here. GitHub Releases remain the source for downloadable packages and complete generated commit notes.

## 0.7.0

- **A session that is opening can no longer be retired out from under the view, so switching to a running session shows its history immediately — and every refresh-style recovery is gone.** The 0.6.10 rows named the stranding call: `session-open {phase: "invalidated", by: "dispose"}` with the stack `startSessionDisposal ← retireScope`, 12 ms and 24 ms after two session opens began, while the conversations afterwards sat at 「载入历史…」 with an empty transcript. The desktop bundle says exactly what that is: `ClientSessions.retain(id, {source})` *starts the open* (`reference.attachOpening(this.manager.get(id).open(), signal)`) and registers the reference, and the navigation it belongs to can release that reference milliseconds later — `replaceMain()` runs on the layout's `navigation` signal, so a fast switch aborts between `retain()` and `selection.set()`. When the released reference was the last one, the scope retires, the manager drops the instance, and `dispose()` runs *while the first page is still in flight*; `openState` stays `"loading"` and nothing is scheduled to try again. The fix is not another repair but a reference: the phone now retains the session itself (`holdSessionOpen()`, source `dsh-on-phone`) in a microtask after the app's `doOpen` starts — a microtask, because `retain()` calls `open()` again and `open()` has not yet wired its own `openPromise` during that synchronous frame — so the app's release can no longer take the count to zero mid-open. The reference is given back as soon as the app owns the session again (`handback {reason: "app"}`), when the instance is replaced or dropped (`"replaced"`, `"gone"`), or after a 60 s grace period (`"expired"`); a stopped surface releases everything it still holds (`"stopped"`). The DOM watch is deleted outright: no placeholder sniffing, no socket rebuild ladder, no reload timer — `src/stuck-view.ts`, `src/socket-watch.ts`, `src/session-resync.ts` and their tests are gone, and the object-layer guard keeps only the in-place round-trip repair for a stale pass and the app's own `resync()` for a first frame that never arrives. Both are reported as `session-open` rows; the fix itself is reported as `phase: "hold"` and `phase: "handback"` with its reason.

## 0.6.10

- **A session the app has already retired is handed back to the app, because no repair on the instance itself can work.** The device log for the 0.6.9 build names the stranding call for the first time and it is not one the view can survive: `session-open {phase: "invalidated", by: "dispose"}` with the stack `startSessionDisposal ← retireScope`, 24 ms after the session was opened, and then six `session/follow` opens over the next 30 s whose sockets each received their own snapshot while the conversation stayed at 「载入历史…」 until the reload. The desktop bundle says what that stack means: the main view holds a session by *retaining* it, and `replaceMain()` runs on the layout's navigation signal — a fast session switch aborts it between `retain()` and `selection.set()`, the reference is released, `retireScope()` drops the instance from the manager and disposes it. `Session.dispose()` only bumps the open generation: the instance the phone keeps rendering stays at `openState = "loading"` forever, and every pass on it waits on a transport bound to a connection generation that is gone — which is why reopening it, resyncing it and rebuilding carriers all failed, and why the orphan answered while the app's managed sessions were fine. The guard now checks, with the app's own manager map, whether the instance it is holding is still the one the app hands out for that id; when it is not, the repair is `uiWorkspace.openSession(id)` — the call the sidebar makes on a tap, which re-retains a current instance, updates the selection and releases the previous reference on the workspace lifetime signal that is never aborted mid-navigation. Reported as `session-open {phase: "reselect"}`; the in-place repair stays as the fallback when the app will not navigate, budgeted separately (six re-selections, one refusal ends the app-level path) so a host that refuses cannot be poked in a loop.

## 0.6.9

- **The stranded `openState` is repaired where it is set, not watched for in the DOM.** Every recovery so far answered the placeholder: the watch saw 「载入历史…」 two seconds in and then chose a lever (reload, socket rebuild, `resync()`, carrier rebuild). Reading the app's own session controller says why none of them removed the stall: `Session.doOpen()` sets `openState = "loading"` *before* awaiting the opening frame, and after that frame arrives it returns early — `if (generation !== this.openGeneration || this.events !== events) return;` — without publishing `openState = "open"`, while `open()`'s own `.finally` has already cleared `openPromise`. The pass is over, the state still says loading, and nothing is scheduled to try again; the generation is bumped only by `resync()`, `dispose()` and `failEventStream()`, so any of them landing mid-open strands the view. The new `session-open-guard` client module wraps the session class prototype (once per prototype, feature-detected, no-op on a shape it does not recognise): a pass that settles with the state still `"loading"` and no open scheduled gets a new `open()` on the carrier that is already up — a round trip instead of a 2 s watch plus a rebuild — capped at two repairs per session per page load, skipped entirely for a session the app has removed. A first frame that never arrives at all is timed out at 1.5 s into the app's own `resync()`, once per session. Both halves report `session-open` rows (`phase: stranded | no-frame`), and the invalidating calls report theirs with a trimmed stack (`phase: invalidated`, `by: dispose | resync`), so the next device log finally names which call strands a session instead of inferring it. The DOM watch stays installed as the outer net.

## 0.6.8

- **The stalled view is handed back to the app before the wire is cut.** Device rows from the 0.6.7 build record a stall the rebuild ladder could not touch: the placeholder was up with an empty conversation while the socket watch reported `sockets: 0` — the app had opened its mux socket before the plugin half was evaluated, so the watch owned nothing to close, every rung of the ladder closed zero sockets and the only lever left was the 30 s reload. The app’s connection service is the lever that does not need ownership: `ctx.get("connection")` exposes `reconnect()`, which aborts the current generation and resets the retry backoff exactly as the app does after a dropped wire. The watch now asks for that rebuild first on every rung and records it as `carrier: 1`; closing a socket remains the fallback for app builds without that method, and the immediate reload is now reserved for the case where neither lever exists.

## 0.6.7

- **The stuck view is re-opened through the app's own session retry before any socket is touched.** Device rows from the 0.6.6 build record the session switch that leaves 「载入历史…」 on screen: the placeholder appears 2.0 s in, the first replacement carrier is up with its own `session/follow` snapshot 3.1 s later and the view is still loading, and only the *second* rebuild recovers it at 13.1 s. Rebuilding carriers is what costs that time — the app loses and re-establishes every subscription it holds (workspace follow, jobs, terminal). The session controller already carries the cheap retry for exactly this state: `resync()` bumps the open generation, disposes the stream and opens again on the carrier that is already up, which is what the app itself does when the viewed session's address changes. The watch now asks for that first, once per stall, and waits a one-second grace before starting the rebuild ladder — so a client-side stall recovers in a round trip while a host that really stopped answering still gets the carrier rebuilt behind it.

## 0.6.6

- **The stalled view is rebuilt in quick succession, because the second rebuild is the one that works.** Device rows from the 0.6.5 build record a session switch that left 「载入历史…」 on screen with an empty conversation while the HTTP side was perfectly healthy: the `session/page` guard had made 13 calls with none in flight, the last answering in 51 ms, and the socket record showed no outstanding `session/follow` open at all — the app simply sat in its client-side `openState = "loading"`. Closing the mux carrier recovered the view, but only the *second* rebuild did: the first replacement socket published its own `session/follow` snapshot 3.1 s in and the view stayed loading, while the second rebuilt it at 13.1 s. Reading the app's own ChatView confirms the hint is rendered purely from `openState === "loading"` with nothing retrying it. The retry ladder is therefore dense at the front — 2 s, 3.2 s, 5 s and 8 s into the stall instead of 2 s, 6 s, 14 s — so the second carrier arrives while the user is still looking at the placeholder, and the 30 s reload stays the last resort.

## 0.6.5

- **A swipe up loads earlier history again after the transcript stops reacting to scroll.** Device rows from the 0.6.4 build show a fresh session open being answered with four history pages and the phone going quiet afterwards: iOS stops sending `scroll` events once the transcript is pinned at its top, and a transcript shorter than the viewport never sends one at all — while the counters that let the fill give up are reset only by that same missing event. One give-up, or one page that did not grow the transcript, therefore left 「加载更早」 unreachable by swiping until the document was reloaded. A finger on the transcript is now itself the request: `touchstart`/`pointerdown` resets the per-gesture budget, and `touchmove`/`pointermove` at the top asks for the next page through the app's own button, throttled to one load per 1.2 s and at most 12 pages per gesture. The fill path stays for a transcript too short to scroll and shares its timestamp with the gesture, so a page is never requested twice; each gesture-driven load posts a `history-gesture` row to the temporary channel while this is verified on the device.

## 0.6.4

- **A stalled conversation view is rebuilt two seconds in, not fifteen.** Device rows from the 0.6.3 build show the app leaving 「载入历史…」 on screen for 5-20 s while the HTTP history page behind it had answered in milliseconds, and that closing the app's mux socket brings the conversation back about a second later — the watchdog was simply waiting 15 s before doing it. The watch now acts at 2 s (the host's own placeholder element plus an empty conversation) and retries the rebuild on a 2x backoff — 2 s, 6 s, 14 s — after which the page reload stays the last resort at 30 s, once per ten minutes. With only the `session/follow` opening frame withheld on the live app the deployed build reports `detected` and `reconnect` at 2.5 s, a second rebuild at 6.5 s and a third at 14.5 s, where the previous build's first close only came with the 45 s reload. Fewer reloads also means less of the shell flash the phone shows while reloading.

## 0.6.3

- **The stuck-view watchdog no longer mistakes a healthy conversation for a stalled one.** 0.6.2's first version searched the whole document for a leaf whose text merely *contained* 「载入历史」, so the moment a message talked about the placeholder — including the release note that announced the fix — the conversation was reported as stuck: on the device the watch closed sockets and reloaded the page at 28 and 46 rendered turns, spent the reload budget, and left the next real stall (`detected` at 0 turns) with its ladder already given up. The detector is now the host's real placeholder element — the `hint` class of the conversation CSS module, which `ChatView` renders only while `openState === 'loading'` — and every action additionally requires an empty conversation (zero `[data-chat-turn]`), so a view that is showing content is never reported, rebuilt or reloaded.
- **The ladder is patient enough for a phone.** A session needs seconds to paint on iOS (measured 7 s for a slow open), so the watch reports at 5 s, closes the app's sockets at 15 s only if the conversation is still empty, and reloads 30 s after that — one reload per ten minutes rather than three per five — never while the page is hidden or offline. With only the `session/follow` opening frame withheld on the live app, the deployed build reports `detected` (5.0 s) → `reconnect` (15.0 s, `stalled: true`) → `reload` (45.0 s), the next generation repeats it, and a healthy session is left untouched: five watchdog rows after the deploy, all at zero turns with the exact placeholder text, no false positive.

## 0.6.2

- **Switching from a finished session to a running one no longer leaves the conversation blank on 「载入历史…」.** The first screen of a conversation is published by the opening `snapshot` frame of the `session/follow` stream carried on the app's mux WebSocket, and nothing in the stack times that stream out or re-requests it: reproduced against a live app by withholding only that one frame, the phone showed the host's placeholder with zero turns and the app never sent another frame on the socket. The client half now watches the page's WebSockets from module evaluation — the earliest point the plugin runs, before the connection layer creates the mux socket — and counts opening frames per follow stream. When the host's placeholder stays visible for 3 s it reports a `stuck-view` row, closes a follow stream that has fewer snapshots than opens so the connection layer rebuilds its generation, and if that did not help within 6 s reloads the page, at most three times per five minutes before giving up and saying so. The same run shows the watchdog closing and rebuilding the transport, reloading three times, reporting `detected`/`reconnect`/`reload`/`gave-up`, and leaving a healthy session (46 turns) untouched.
- **A history page call can no longer hang the view.** The host asks for `/api/session/page` with a plain `fetch` and no signal, and nothing else in the chain times out either, so one POST that dies on a half-open socket never settles while the view waits on it forever; seven such POSTs around one blank conversation left no server-side record at all, because the proxy only writes a page row once the phone has drained it. That call is a read-only, idempotent RPC with a JSON string body, so `globalThis.fetch` is now wrapped for that endpoint alone: 8 s for the headers, 20 s for the body, three attempts with a short backoff, and a `page-fetch` row whenever a call needed more than one attempt or failed. A caller abort passes straight through and is never replayed, every other request and every non-string body goes untouched, and the wrapper is removed on teardown. A real browser confirms the host reads `globalThis.fetch` at call time, so a wrapper installed after boot still observes the page POSTs.
- **A page is small enough to arrive and is now measured on the phone.** The first page drops from 20 to 12 messages and the continuation page from 60 to 24 (turn-window floor 10 to 8), because a phone cannot paint a 0.9–1.8 MB JSON page (219–538 KB compressed) until the last byte lands. The proxy's own row now records the bytes counted on the way to the phone and `ms` up to the socket flush, plus `upstreamMs` for the local app alone — the previous numbers stopped at the app's last byte and read as milliseconds while the phone was still waiting. New `src/page-timing.ts` reads the phone's resource timeline for `/api/session/page` and samples how many turns are rendered 0/250/1000/3000 ms after the last byte, so a slow payload and a slow paint can be told apart, and the timeline buffer is raised to 2000 entries because Chrome stops recording once its 250-entry buffer fills (the app makes two cost-meter calls a second, which filled it on its own).
- **A sideways swipe over the open-files strip picks a file again.** Traces show every such swipe happening with `scrollWidth === clientWidth`: the open files fit, there was nothing for the browser to pan, and the host's pointer drag — which floats a pane out and dims the page with its dock scrim — answered instead. `installStripSwipe()` now hands the gesture to the browser while the strip still has room in that direction and takes it over when it has none, swallowing the tap it would otherwise synthesize; the global tap feedback no longer leaves the pane host at opacity 0.72 while every neighbour sits at 1.
- **The composer's status and footer take two rows instead of stacking into the conversation**, and the phone's history telemetry, gesture rows and page waits are the temporary diagnostic channel behind `~/.dsh/mobile-telemetry.jsonl` (removed once the stalled-view case is confirmed closed). The test suite no longer writes into the real DSH home while it runs.

## 0.6.0

- **The desktop "移动访问" panel is remote-only now.** The LAN card in that panel was the last desktop surface advertising the app download and the QR-code / pairing-key / pairing-link flow, while the shipped remote path is Tailscale Serve and needs no pairing at all: the panel offered two competing stories and a phone could not tell which one the computer was actually serving. The panel is back to the single view upstream 0.4.9 had — remote address (**复制地址**), enable/disable, one status line, **Reconnect**, and **Diagnostics** — so the app-download row, the LAN/remote tab switcher, the QR box, the pairing key and link buttons, and the paired-device list are gone. The remote view is visible by default, and the panel's status strings no longer fall back to LAN wording.
- **The sidebar entry lines up with the entries around it.** The trigger under **插件 / 移动访问** kept `justify-content: center` and `padding: 6px 10px`, so its icon and label floated in the middle of the footer column while 导入会话 and 设置 sat on the left line; 0.4.9's `flex-start` / `6px 8px` is restored, and the entry now starts at the same x as its neighbours.
- **The documentation describes one channel.** `README.md` / `README.en.md` are rewritten in upstream's shape: install from source, enable Tailscale Serve, open the address on the phone, customize with `/mobile`, plus a narrower configuration table (the LAN keys are no longer documented). The `dsh-mobile setup` hint that pointed at the panel's pairing key is gone from the CLI output, and the package description no longer advertises LAN access or an Android app.

- **The Android app is gone, with everything that built it.** The phone reaches DSH through the browser, so `apps/mobile/` (66 files: the Gradle project, the contract fixtures, the store assets) is deleted, and so are the pieces that existed only to ship it: the `android` jobs in `.github/workflows/ci.yml` and `.github/workflows/release.yml` (the release job no longer waits for a signed APK), the Gradle entry in `.github/dependabot.yml`, the Android signing-secret requirements in `CONTRIBUTING.md`, and `scripts/check-mobile-release.mjs` — whose brand, launcher-icon and network-security assertions had drifted into doing nothing while still running inside `npm run verify`. `scripts/check-release-version.mjs` no longer cross-checks `build.gradle.kts`, and `npm run verify` no longer runs the mobile-release gate.
- **A tag releases through GitHub Releases only.** The workflow's `publish` job ran `npm publish` (or `--provenance` through OIDC), and `github-release` waited on it, so a tag that could not publish to npm produced no release at all. Publishing to npm is not how this fork ships: the job is gone, and a `v*` tag now gates the version, packs the plugin, and creates the GitHub Release with the tarball, its SHA-256 and the CycloneDX SBOM.
- **Package metadata points at this fork.** `repository`, `bugs` and `homepage` named `saya-ch/dsh-mobile`; they now name `qiushenjie/dsh-mobile-tailscale`. The upstream project stays credited in the README and LICENSE. The `android` keyword is gone.
- **`TROUBLESHOOTING.md` and `SECURITY.md` describe the remote channel only.** The LAN-gateway section (port 3443, mDNS discovery, `setup.json`, device discovery) is deleted and the remaining sections are renumbered; the health checklist checks the plugin's self-reported remote state, the 443 ownership and the remote origin instead of a LAN listener, and the security policy now states the deployment rule as "Tailscale Serve on the tailnet only, never Funnel and never port forwarding", with the Android CA / WebView / cpolar paragraphs and the pairing-key flow removed.

## 0.5.1

- **Typing a space or a symbol into the phone's terminal did nothing.** The repair added for the repeated-first-character bug re-dispatched the keystroke as a synthetic `KeyboardEvent`, which never reaches the pty: xterm ignores the `keyCode 229` an iOS software keyboard reports, and nothing downstream re-reads a synthetic keydown, so the character was dropped even though the repair reported success. The repair now writes the character into xterm's own `.xterm-helper-textarea` and dispatches the `input` event xterm actually listens for, re-querying that textarea on every injection because xterm replaces the node (holding the stale node silently dropped every second identical character). The `keyCode 229`/`0` gate stays — a real IME commit already delivers the character, and repairing it as well would double it, which is why the evidence listeners still cancel the repair for the rest of the quiet window.
- **The right drawer could not be scrolled vertically on iOS.** Every descendant of the open drawer carried `-webkit-overflow-scrolling: touch`, which on iOS gives each of them its own momentum scroller: the pane's real scroll container then sat inside a nested one and never received the gesture, while Chrome ignores the property and scrolled fine — a device-only failure that every desktop check missed. The property is gone from the drawer (the sidebar list and the table scroller, single scrollers both, keep it), and `drawer-pan.ts` adds a fallback that only takes over after the browser has had its first move: `drawerPanDecision()` returns `wait` for the first `touchmove`, `native` as soon as the browser scrolled the container itself, and `manual` — writing `scrollTop` from the finger delta — only when it demonstrably did not.
- **Every response on the remote channel now carries a cache policy.** The passthrough proxy wrote its own sanitized headers, and dropping the upstream `cache-control` without putting one back left the answer open to heuristic caching: a phone could keep an old document, which keeps naming an old bundle revision, so a client fix never arrived even though the server was serving it — and the whole shell (measured: 6.6 MiB gzipped in first-load requests) was re-downloaded whenever it did not. A revisioned `/plugins/**` bundle or a hashed `/assets/**` file is now `private, max-age=31536000, immutable`; anything else is `no-cache`, and an upstream `no-store` is kept verbatim.
- **The remote origin could silently disappear while the panel still reported "ready".** `tailscale serve` ownership was decided from memory alone: teardown ran `serve --https=443 off` unconditionally, so a controller closing after a newer one had registered for the same loopback port took the phone's origin down with it (observed live after a plugin reload), and nothing ever noticed when the daemon dropped the entry on its own. Teardown now reads `serve status --json` and clears the port only when the registered handler still points at this controller's own loopback origin, `reconcile()` re-registers a missing entry, and a watchdog runs that check 5s after enabling and every 60s after — the panel's claim and the node's reality can no longer drift apart unnoticed.

## 0.5.0

- **Re-baselined on the 0.3.5 line.** This release is the code of commit `41d1b93` (2026-09-17, the last commit published as `0.3.5`) re-versioned as `0.5.0`, plus only the adaptation the current official DeepSeek Harness `0.1.7-rc.2` needs. None of the 0.3.6–0.3.21 work is included, and neither is any of the 0.4.x work: there is no connection watchdog, no key repair, and no serve-only pivot in this build.
- **The plugin can activate on `0.1.7-rc.2` again.** The four `@deepseek-ai/*` peer ranges and `SUPPORTED_DSH_VERSIONS` now list `0.1.7-rc.2`. Without the peer range the loader refuses the plugin outright — `Plugin dsh-mobile-tailscale@0.3.5 is incompatible with dsh 0.1.7-rc.2 … Exact-version exemption: not active` — and the whole plugin disappears from the tree.
- **A layout contract this build does not implement no longer replaces the stock layout.** DSH `0.1.7-rc.2`'s stock layout module declares `@deepseek-ai/dsh-client-shortcuts` as a dependency (and no longer `@deepseek-ai/dsh-client-runtime`) and registers the `sidebar` / `main` (keyed) / `rightbar` / `shell.overlay` / `shell.leading` slots, while this fork's `mobile-layout.js` declares `conversation` / `details`. The document rewriter replaced the layout module unconditionally, which on this generation leaves the conversation with no slot to render into. It now replaces the module only when every dependency it declares is one the matched profile knows; otherwise the stock layout stays and `native-mobile.ts` adapts the stock DOM.
- **Known, unchanged by this release.** `载入历史` on a stalled page is official client behaviour: `@deepseek-ai/dsh-client-ui-chat` owns that state and the 0.3.x line never had reconnect self-heal, so this build neither causes nor cures it. On this DSH version the phone graph also still carries `dsh-better-sidebar`, whose client module requires `@deepseek-ai/dsh-client-ui-primitives` (absent from the served graph, so it throws `Minified React error #130`); `dsh-rewind-plugin` fails the same way in `conversation.session.header.actions` (`TypeError: Cannot read properties of undefined (reading 'filter')`, from an undefined `snapshot.queue`) when it is installed. The 0.3.x line dropped both from the phone graph from 0.3.17 on, and that work is deliberately not part of this re-baseline.

## 0.3.5

- **The mobile settings ordering had silently stopped running.** `orderAuthenticatedSettings` located this plugin's boot-manifest entry by the literal id `dsh-mobile`, but the entry id is the published package name (`dsh-mobile-tailscale`). The lookup found nothing and returned early, so the code that orders the authenticated settings module after this plugin never executed; DSH then resolved its settings to the in-memory backend on every mobile page, which surfaced as "settings are unavailable in this browser" and an unloadable model provider directory. The id is now derived from `package.json` (and the `tsdown` module-loader banner reads the same source), the stale requirement that the settings module depend on `connection` was dropped — DSH 0.1.2 moved its one-time `$host.isLoopback` read and declares only `@deepseek-ai/dsh-api-remotes` — and the test fixtures now match the real manifest shape, so a future drift fails a test instead of silently skipping the work.
- **The remote channel never rewrote its document.** `serveRewrittenDocument` gated the rewrite on a declared `Content-Length`, but DSH answers the application document with `Transfer-Encoding: chunked`, so every request skipped the rewrite. The body is now buffered to a bound instead, and a non-identity `Content-Encoding` skips the rewrite rather than feeding compressed bytes to a parser. A rewrite failure still serves the stock document, so the remote channel degrades instead of failing closed.
- **Opening the composer model menu closed it again.** The programmatic-focus guard meant to stop the iOS keyboard from popping on session open blurred *any* non-tapped text field. Drilling into the model list autofocuses its search field, so that blur fired the menu's own blur handler and dismissed the overlay; the sibling "推理等级" pane, which has no search field, was unaffected. The guard now covers only the composer editor it was written for.
- **A sidebar row's action menu was torn down by the row's own tap.** The portrait auto-collapse treated a tap on a row's ellipsis menu as selecting the row and collapsed the sidebar 240ms later, taking the just-opened menu with it. Only a row-body selection collapses the sidebar now, matching the guard the dedicated layout already had.
- **The "移动访问" entry shared a footer row with other plugins' entries** and was pushed past the sidebar edge, where the resize divider clipped it. The footer action row is allowed to wrap and this entry claims its own line, with its icon and label centered together.
- **The Android bridge's interactive actions cannot succeed.** `startPending` answers `files.pick` and `camera.capture` synchronously with `{ok:false, code:"pending"}`, and the page adapter rejects and forgets any non-`ok` reply, so the real asynchronous reply is dropped. Recorded here rather than changed: the fix needs a device to verify against.
- **Selecting a model on the phone did nothing.** The authenticated-transport trust was installed too late to survive DSH's own memoization. `@deepseek-ai/dsh-client-connection` builds its handle with `isLoopback: transport?.ownsHost === true || <loopback hostname>`; this plugin instead let `isLoopback` default to `false` on the phone and flipped it from the mobile client module's `apply()`. But `@deepseek-ai/dsh-api-gateway` snapshots `isLoopback` into cached `$host` facts keyed **only** on `home`, which is stable on the remote channel — so whichever module read `ctx.remote.$host` first froze `isLoopback: false` for the life of the page, and `dsh-client-ui-settings`, `dsh-client-ui-settings-general` and `dsh-api-session-controller` all read that cached value. The plugin now injects the pre-boot `window.__DSH_TRANSPORT__ = { ownsHost: true }` override that upstream ships, so the handle is born loopback-trusted on both channels, and `@deepseek-ai/dsh-api-gateway` is ordered after the mobile client on the remote-backed settings graph — both halves of the upstream 0.3.4 fix, which this fork had dropped while keeping only the settings edge. The injected statement deliberately does not throw when an override already exists: it shares a script block with the boot-manifest assignment, so throwing would blank the whole mobile page.

- **Tapping a model row on the phone sent no request at all.** A finger tap dispatches `mousedown`, whose default action moves focus out of the menu container — and that container closes itself from its own blur handler. It therefore unmounted between `mousedown` and `mouseup`, no `click` was ever dispatched, and the row's handler never ran: no request, no error, no toast, unchanged label. Only the deepest level broke because the model pane autofocuses its search field, while drilling from one root-pane cell to the other keeps focus *inside* the container and never blurs it — and a synthetic `click` (which dispatches no `mousedown`) always worked. `native-mobile.ts` now cancels just the `mousedown` default for a press on a menu item while focus is inside that item's menu, keeping the overlay mounted so the click gets through; cancelling `touchstart` or `pointerdown` instead would suppress the very click being delivered. Verified on the device against the emitted page, the RPC frames, and the host's own `session/modelCatalog` and `settings.yaml`.

- **The remote channel could reach the loopback-only administration surface.** The passthrough proxy rewrites `Host`/`Origin` to the loopback upstream, so anything it forwards arrives at the DSH WebServer looking exactly like a request from the local machine — and that surface is guarded by that loopback assumption alone. The LAN gateway already refuses its own admin prefix (`/api/mobile-access*`) on its own listener; the proxy did not, so any device on the tailnet could `POST /api/mobile-access/lan/pairing/open` and receive a complete pairing token and link, or list, revoke and clear the paired LAN devices — escalating tailnet membership to LAN-device trust. Reproduced against a live deployment before the fix (201 with a token, 200 with gateway state); now refused with `404 not_found` before the forward, on both the request and upgrade paths.
- **A disabled remote switch no longer clears `tailscale serve`.** `initialize()` ran `tailscale serve --https=443 off` whenever the persisted switch read disabled, and a fresh install persists exactly that — so booting DSH would tear down an unrelated 443 entry the user configured themselves, for a plugin that never owned it. A disabled switch means this plugin does not own `serve`, not that `serve` should be cleared; an explicit disable still clears the entry the plugin created.
- **A failed start no longer leaves the serve entry pointing at a closed proxy.** `runServe` registers the 443 entry before `resolveOrigin` reads the MagicDNS name back, so a failure after the registration left `serve` forwarding to a proxy the error path then closed — the phone saw connection-refused while the panel reported only a generic error. The error path now clears the entry it just created.

- **A port-443 conflict is reported as such.** The recovery path raises its own errors, and their wording ("…is occupied by another service") matched none of the message patterns the classifier looks for, so the panel showed the generic `serve_failed` and lost the actionable hint. Those failures now carry `serve_port_conflict` explicitly rather than relying on wording.
- **Release tooling that had drifted into doing nothing.** `scripts/check-mobile-release.mjs` defined its brand/store-icon and Android checks but never called them, so it exited 0 with no output while sitting inside `npm run verify`: every assertion it holds, including the pinned-certificate and network-security contracts, was unenforced. It now runs them. The release workflow's idempotence probe queried `npm view "dsh-mobile@$version"` — the upstream package — while this one is `dsh-mobile-tailscale`; because upstream publishes the same version numbers the probe matched and the publish step reported "already published" and skipped, so this package was never on npm while the GitHub release was still created. The name is now read from the packed manifest. The `files` whitelist also omitted three sourcemaps (`index.mjs.map`, `cli.js.map`, `index.d.mts.map`) that the shipped bundles reference.
- **Opening a project in the sidebar collapsed the sidebar.** The Workspace (project) header and a session row are both `div[role="treeitem"]`, but only the header carries `aria-expanded` — its click toggles the nested session list — while only a session row carries `aria-selected`, whose click opens the conversation. `selectsSidebarRow` decided purely on whether the tap resolved to a `button` ancestor, and a project title is a plain span, so the one gesture that opens the list was read as selecting a session: the portrait drawer closed 240ms later, over the list the user had just opened. A row that announces `aria-expanded` is now never a selection, and the dedicated layout's own drawer guard gained the matching `:not([aria-expanded])` so both layouts encode the same rule instead of only one. Covered by a regression test that fails without the guard.

## 0.3.3

- **An unverified Host version no longer aborts activation.** `assertSupportedDshVersion` threw from the first statement of `apply()`, so a version outside the verified set failed its loader entry, failed the whole plugin tree, and made DSH Desktop stop the harness and fall back to its safe-mode profile with **every** third-party plugin disabled. Activation now warns (`DSH_MOBILE_UNVERIFIED_DSH_VERSION`) and continues; the strict assert remains available for callers that want it.

- **Fix a 30-day timer overflow on the remote channel.** The pairing-free remote guest authorization used a 30-day (`2 592 000 000 ms`) expiry, and the derived abort/close delays were passed straight to `setTimeout`, which truncates any delay above `2^31 - 1 ms` (~24.85 days) to **1 ms**. Every remote request and WebSocket was therefore aborted immediately, logging `TimeoutOverflowWarning` and `upstream_unavailable (socket hang up)` in the harness log. Session-derived delays are now clamped to `MAX_TIMER_DELAY_MS`.

## 0.3.2 - 2026-08-29

- **Remote channel no longer hardcodes the web port.** Tailscale Serve now targets a plugin-owned loopback passthrough proxy that resolves the live upstream from the host `webServer` service per request (falling back to `DSH_WEB_URL`, then `upstreamOrigin`). The remote channel follows DSH Desktop's random per-launch web port automatically — no manual `tailscale serve` re-pointing after restarts.
- **Browser-trust fence bypass for remote.** The passthrough proxy rewrites `Host`/`Origin` to the upstream origin (the same proven pattern as the LAN gateway) and injects the upstream session cookie, so phone `/api` calls no longer hit the DSH browser-trust fence 403 while staying pairing-free.
- **Automatic stale serve-config recovery.** Starting Serve now detects a port-443 occupancy (`already serving TCP` etc.), clears it when 443 is the only serve entry, and retries once; a conflict with other serve entries surfaces a dedicated `serve_port_conflict` error instead of the generic `serve_failed`.
- **LAN gateway upstream follows the live instance too.** Both LAN and remote paths resolve the upstream through the webServer service, so neither depends on a fixed port being occupied by a particular instance.
- **Transparent WebSocket passthrough.** The proxy forwards every upgrade request (any path, query preserved) instead of whitelisting three core channels, so plugin channels such as `/sidebar/ws/agent-opens` and `/sidebar/ws/agent-terminals` keep working remotely. Upgrade failures now log a diagnostic line to the harness log instead of being masked as an EOF.
- **Pairing-free mobile-frontend assets on the remote path.** The DSH WebServer mirrors the LAN gateway's mobile metadata, custom css/js, mobile layout module and extension registry (without the LAN device-pairing requirement), so the phone's mobile UI features load over the Tailscale Serve channel too.
