# Changelog

Notable changes to DSH Mobile are recorded here. GitHub Releases remain the source for downloadable packages and complete generated commit notes.

## 0.4.0

- **The local-network channel is removed entirely; Tailscale Serve is the only connection left.** The self-signed "DeepSeek Harness Mobile CA" chain was trusted by nobody: it was never added to the Mac keychain, and no route ever sent it to the phone, so both the phone and the Mac's own browser stopped on the certificate interstitial while the phone never reached the `3443` port at all. The `https://<node>.<tailnet>.ts.net` address, by contrast, carries a real Let's Encrypt certificate and takes its access control from tailnet membership, so 0.4.0 deletes the redundant and unusable half and keeps the one that works. Removed in this release:
  - the LAN HTTPS gateway and its `:3443` listener;
  - pairing links, pairing tokens, and QR codes; the paired-device list, revoke, and reset operations;
  - `$DSH_HOME/mobile-access/tls/` (`ca.pem`, `ca-key.pem`, `dsh-mobile-ca.cer`, `server-cert.pem`, `server-key.pem`) and every certificate the plugin used to issue for itself;
  - the `dsh-mobile setup` subcommand in full — LAN interface selection, certificate issuance, and the Windows firewall rules it wrote. **`dsh-mobile setup` no longer exists and has no replacement**: the remote path needs no initialization. Running it now fails with `unknown command: setup`;
  - LAN-related diagnostics and health checks, the DNS-SD/mDNS `dsh-mobile` advertisement and its periodic UDP announcements, the `computer-images` extension, and every `/api/mobile-access/lan/*` admin endpoint;
  - the desktop panel's 局域网 tab, its 生成配对链接 button, and the pairing QR code. The tab switcher itself is gone too: the 移动访问 card now has a single view — the remote address with a 复制地址 action, an enable/disable switch, a status line, a reconnect action, and a 诊断 section (the `POST /api/mobile-access/remote/reset` route stays available to tooling, but no button drives it);
  - the npm dependencies `bonjour-service`, `selfsigned`, and `qrcode`.
- **What remains is the remote channel you already had.** The plugin still registers and owns its own 443 serve entry (`tailscale serve --bg --yes --https=443 http://127.0.0.1:<port>`) and clears only that entry on shutdown, so a Desktop restart does not disturb another process's registration. The phone opens `https://<node>.<tailnet>.ts.net` over a valid Let's Encrypt certificate; the prerequisite is that the Mac and the phone are signed into the same tailnet with Tailscale running on the phone, and tailnet membership is the access control — there is no login page and no pairing. Remote on/off state continues to live in `$DSH_HOME/mobile-access/remote/control.json` and the provider choice in `$DSH_HOME/mobile-access/remote/provider.json`; custom phone CSS/JS stay at `$DSH_HOME/mobile-access/mobile.css` and `mobile.js`. The LAN-era `$DSH_HOME/mobile-access/control.json` is no longer read.
- **The phone front-end rewrite is unchanged.** Boot batches for a smaller first paint, the session-window clamp (the phone asks for 10 messages per follow/history request instead of hundreds), and the optional dedicated mobile layout selected by `mobileLayout` (`auto` | `mobile` | `stock`, default `auto`) all still apply, now on the single remote channel.
- **The two READMEs were cut to about 140 lines each.** They had grown into a manual: three separate install walkthroughs, the internal serve-registration and 443-ownership mechanics, a version-by-version optimisation log, an admin endpoint table and a full compatibility matrix. The READMEs now carry only what a user needs — install, use, customise, configure, troubleshoot — and hand the depth back to `TROUBLESHOOTING.md` (which already documented it), `CHANGELOG.md` and `SECURITY.md`. The install order also follows reality now: the package is not on npm yet, so building from source is the primary path and the `@latest` command is documented as what it becomes once published.

## 0.3.21

- **The LAN address went back to being usable by a phone that had never paired, after 0.3.20 removed the only control that could pair one.** An unpaired device that opens `https://<lan-ip>:3443/` is answered `302 /mobile-access/login`, and that page tells it to pair from the computer — while the pairing page itself (`GET /mobile-access/pair`) answers `404` unless a pairing window is open, and the window could only be opened by the 生成并复制密钥 / 复制配对链接 buttons that 0.3.20 deleted. The 局域网 tab now carries exactly one control again, 生成配对链接, which opens a pairing window through `POST /api/mobile-access/lan/pairing/open` and copies the resulting link (`…/mobile-access/pair#instance=…&token=…`, 120 s by default, single use, one device). Everything else the tab used to hold stays removed: no on/off toggle, no device list, no client download. When the clipboard is refused the link is printed in the panel so it can be copied by hand. The button is offered only where the admin route can answer at all (the desktop shell and loopback pages), so a phone opening this same panel never sees a control that would be refused.
- **The pairing QR code is rendered under that control again, and it is now scannable.** The route always returned `qrSvg` for the same one-time link, so the panel draws it (white plate, caption) beside the copied link, clears it when another window is opened, and never shows it on a phone's own copy of the panel. The first version was unreachable by a camera: `qrcode` was called with `margin: 1`, so the 53-module code carried a one-module quiet zone instead of the four the spec requires, and the 168 px plate left ~3 px per module against the dark panel. The SVG is now generated with `margin: 4` (61 modules) and the panel sizes it to the nearest whole-module multiple of 244 px, so modules stay square and the quiet zone survives; a Vision decode of both renderings confirmed the payload was always correct and the old geometry is what a phone struggles with.
- **The remote channel answered `404` for the health path the diagnostics probe, so a healthy `ts.net` address was reported as unreachable.** `defaultRemoteProbe` fetches `/mobile-access/health`, which only the LAN gateway served; upstream does not know the route, so the public-address check failed on the channel that was in fact answering `200` in 27 ms. The remote proxy now answers that path itself with `{"ok":true}` (`no-store`, `GET`/`HEAD` only, unauthenticated because a phone probes it before it holds any credential), and the LAN check no longer claims 配对入口可用 when no pairing window is open.
- **Repository pointers and the user-facing documentation were brought in line with what this fork actually is.** `package.json` (repository/homepage/bugs) and `SECURITY.md` still sent users to the upstream `saya-ch/dsh-mobile`; the READMEs, `TROUBLESHOOTING.md`, the two `apps/mobile` READMEs, `SECURITY.md`, `THIRD_PARTY_NOTICES.md` and `CONTRIBUTING.md` were rewritten against the current code — the panel that no longer has an on/off toggle or a device list, Tailscale Serve as the only remote provider (no Funnel, no cpolar), the local admin endpoints that now own LAN control, Node `^22.19.0 || >=24.0.0`, the same-version reinstall step, and the 0.3.15–0.3.20 behaviour (revisioned asset caching, the 10-message session window, the pruned modules, `mobileLayout`, the 443 serve ownership) that the docs had never mentioned.

## 0.3.20

- **The 移动访问 panel now shows a phone the address it needs and nothing else.** the client download entry is gone, and 局域网 keeps only the browser address: the 生成并复制密钥 / 复制配对链接 buttons, the pairing QR, the device list behind 管理配对设备 and 清除所有设备, the 扩展：N 个已加载 line and the 开启/关闭局域网访问 toggle were removed together with the request handlers, the render state and the now-dead styles behind them (108 lines removed, 9 added). The LAN gateway keeps the state it already persisted (`control.json`), so the address a phone already opens stays served, and 远程访问 / 诊断 are untouched. Pairing keys are no longer generated from the desktop panel, so key/QR pairing has no desktop counterpart left — the LAN address is the supported path.
- **A restart could delete the tailnet registration the next process had just made, leaving the phone's `ts.net` address refused while the panel reported `ready`.** `tailscale serve --https=443 off` is node-global and teardown ran it unconditionally, so a relaunch that started the new process first — which registers its own proxy and reports `ready` — had that registration removed by the outgoing process. Observed on this machine: `tailscale serve status` answered `No serve config` while the control panel reported `running: true, state: "ready"` and the LAN address kept working, so the phone's remote address was dead while every status signal said otherwise. Shutdown now reads `serve status --json` and clears the 443 entry only while it still points at this instance's own proxy, and an entry another process registered is left alone (the start-failure cleanup uses the same check); an unreadable status keeps the old, unconditional behaviour.
- **The 移动访问 row in the sidebar footer is left-aligned with the rows above it.** The trigger was `justify-content: center` with a 10 px inset while 余额 / 今日 are drawn by `dsh-cost-meter` with an 8 px inset, so the row sat visibly inboard of them; it now uses `justify-content: flex-start` and the same 8 px inset. The collapsed rail keeps its centred icon.

## 0.3.19

- **A dedicated layout for DSH 0.1.7's layout generation, behind an explicit switch.** The generation that ships `main` (keyed), `rightbar` and `shell.leading` replaced the `conversation`/`details` root this plugin's layout module implements, so since 0.3.11 a phone has rendered DSH's desktop frame with the plugin's surface adaptation on top. A CDP trace of one left-sidebar toggle on that frame measured 591 ms of main-thread work at 6x CPU throttling — 141 ms of React click handling, 99 ms of style recalculation, 106 ms of paint, 48 ms of layout — and none of it was this plugin's code (`MutationObserver` disabled: 634 ms; transitions disabled: 562 ms). `mobile-layout-next.js` implements the same contract for a phone: the sidebar and right panel become drawers, the keyed `main` slot renders the selected panel full width, and the service consumers call (`toggleSidebar`, `selectPanel`, `panelInfo`, `beginNavigation`, `openRightbar`, `closeRightbar`, `dispose`) is provided by this module. `/mobile-access/mobile-layout-next.js` is served by the gateway and by the remote proxy.
- **The switch is `mobileLayout`, default `auto`, so nothing changes until it is turned on.** `auto` keeps the current behaviour exactly (a dedicated layout only where the module implements the generation, i.e. DSH before 0.1.7); `mobile` additionally serves the new module on the current generation; `stock` never replaces the upstream layout. The setting lives with the plugin's configuration (`- id: mobile-access` / `config: mobileLayout: mobile` in the profile's patch layer, or the plugin card when the field renders there), so a phone that reacts badly to the new frame can be returned to the stock one without reinstalling anything.

## 0.3.18

- **The opening window still outgrew the size the phone asked for, because a Turn window is a floor and not a bound.** `paginate` walks the log backwards and cuts at whichever comes first — the message count reaching `maxMessages`, or a `turn/start` once `count >= minMessages` and the Turn count reaches `minTurns` — so leaving `{"minMessages":50,"minTurns":2}` in the request let a 50-message page arrive as 291 records. Measured over the tailnet on an idle long session at 6x CPU: 797 KB of snapshot, 291 records, 1588 ms of main-thread work, a 650 ms frame gap and 3870 DOM nodes. The phone now asks for 10 messages with no Turn floor and gets 190 KB, 60 records, 1178 ms, a 383 ms gap and 1828 nodes, with `hasMore: true` so 加载更早 still pages backwards. The same clamp is applied to the `session/page` and `session/history` bodies for clients that page over HTTP.
- Measured server side, the history itself was never the slow part: the snapshot's first frame arrives with the request (0–1 ms) on the tailnet path, so the remaining cost is the client rendering what it receives.

## 0.3.17

- **The phone's right-sidebar panes were rendered by a plugin that cannot work on DSH 0.1.7, so opening the 文件 pane showed only a 重试 button that kept failing.** Measured live: `dsh-better-sidebar`'s client calls `require("@deepseek-ai/dsh-client-ui-primitives")`, and 0.1.7 no longer puts that module in the client graph (the served manifest carries 71 entries and none of them is it), so the import resolves to `undefined` and every pane it renders dies with `Minified React error #130`; its host half fails to activate too (`sctx.settings.register is not a function`). `dsh-rewind-plugin` is broken the same way in a different place: it reads `snapshot.queue` from a session snapshot 0.1.7 no longer sends and throws `TypeError: Cannot read properties of undefined (reading 'filter')` from `collectPendingTargets`, crashing the `conversation.session.header.actions` slot on every render. Neither module is injected by any other entry (checked against the served manifest), so both now leave the phone graph entirely — the phone falls back to DSH's own sidebar and message actions, and 964 KB leaves the boot payload with them. The desktop window keeps both plugins.
- Measured effect on the phone path: `dsh-better-sidebar` 899,862 bytes and `dsh-rewind-plugin` 64,216 bytes no longer download or execute, and the two client-side crashes above stop appearing in the page's error stream.

## 0.3.16

- **The phone asked for 500 messages every time it opened a session, so a long conversation opened slowly and stayed slow to interact with.** DSH 0.1.7 does not fetch a session's history over HTTP at all: `session/follow`, every Gateway stream, travels the WebSocket mux at `/api/remote.mux` as a text frame. Captured on this machine's phone path, a page load and every session tap sent `{"type":"open","endpoint":"session/follow","payload":{"args":{"request":{…,"assistantStream":true,"maxMessages":500,"turnWindow":{"minMessages":50,"minTurns":2}}}}}`, so opening a 35-turn conversation pulled hundreds of records, rendered them, and then re-rendered that DOM on every later tap — while the same page with a short session stayed responsive. The plugin's own history trim had never seen this request: it matches `POST /api/session.history`, which no DSH 0.1.7 client calls, so every earlier history fix was inert. The page now caps the window at DSH's own page size of 50 in the frame that asks for it (`maxMessages` above 50 is rewritten to 50; the `turnWindow` floor stays at 50, which a 50-message page satisfies), and every other frame is forwarded byte for byte. The HTTP trim is also kept and extended to the `session/page` and `session/follow` spellings for clients that page over HTTP.
- Measured effect: the opening window for a long session drops from the desktop's 500-message request to 50, the history the phone downloads and mounts falls with it, and scrolling up still pages through `session/page` (`加载更早`) as before.

## 0.3.15

- **The remote (Tailscale) channel stripped every freshness header from the assets a phone reloads.** The proxy removes `cache-control` and `expires` while forwarding (`BLOCKED_RESPONSE_HEADERS`) and, unlike the local-network gateway, never re-applied `revisionedStaticCacheControl` afterwards, so a phone reloaded and re-parsed the same revision-addressed files every time: measured with `curl -D -` through the remote channel, `@changfenhuang/dsh-genui/assets/mermaid.js?rev=…`, `assets/three.js?rev=…`, `assets/vendor-CCJJTK99.js`, `assets/index-Q6zc2uHV.js` and the stylesheets answered with only `content-type`, `date`, `Connection`/`Keep-Alive` and `Transfer-Encoding: chunked` — no `cache-control`, no `expires`, no validator. A warm-cache reload of the phone page therefore still transferred 5.66 MB (15.44 MB decoded, of which ~5.7 MB is exactly those files), and with no validator the browser cannot reuse its code cache for them either, so the parse and compile cost was paid again on every navigation. Content-addressed URLs (`/plugins/**?rev=`, `/assets/**-<hash>.<ext>`) now keep `private, max-age=31536000, immutable` on both channels; `/plugins/events` and the rewritten document stay uncached.
- Measured effect on this machine's phone path: the files above go from a full re-download per navigation to a 304 (0 bytes), while the assembled batches were already cached that way. The phone's remaining page-boot cost is structural — the DSH 0.1.7 client graph is 75 entries / 10.3 MB of script that any browser client must download and materialize, and DSH's loader rejects a manifest whose entries belong to no initial-load batch, so a phone cannot be served a lazily-loaded subset without dropping plugins outright.

## 0.3.14

- **Every phone page still fetched the whole unpruned boot graph through the document's preload hints.** Since 0.3.11 the served manifest names batches this plugin assembles itself, but the document kept the two stock `<link rel="preload" as="script" href="plugins/??…">` hints DSH writes next to that manifest, and the browser fetched them regardless: measured through the Tailscale channel on DSH 0.1.7, 10.62 MB and 4.20 MB of decoded script naming 58 and 17 modules — including the 5.28 MB `@deepseek-ai/dsh-client-ui-settings-account` that pruning had just removed — against 9.8 MB decoded (2.47 MB gzipped) for the batches actually activated. The hints are now dropped, because the manifest activates batches this plugin answers from its own store and there is nothing left for a hint to warm.
- **The HMR event stream put a pruned module back on the wire.** `@deepseek-ai/dsh-client-hmr` subscribes to the host's `/plugins/events` stream and applies every `{"type":"graph"}` frame to the page's module controller, which then loads anything the stock graph lists that the page has not loaded yet — 5,281,132 bytes for `@deepseek-ai/dsh-client-ui-settings-account`, 526 ms after first paint. Both mobile channels now answer a request that names exactly one pruned module with an inert registration (an empty namespace) instead of the bundle, so the controller's sync is satisfied and the bytes never leave the machine. Stock phase requests, which name many ids and are answered by the upstream's own combination, are left untouched.
- Measured effect on this machine's phone path: 35.4 MB decoded / 25.7 MB transferred before, 5.35 MB transferred after (batches cached; +2.47 MB gzipped on a first visit), with the remaining large items belonging to a third-party plugin that eagerly imports mermaid and three.js.

## 0.3.13

- **The remote (Tailscale) channel forwarded the browser's largest history page untouched.** DSH's browser client opens a session with `maxMessages: 500` and a Turn window of 50 messages, and one page of this session's log measured 1.33 MB against 0.16 MB for 50 messages — downloaded and rendered in one go on a phone, which is what makes opening a long conversation crawl and scrolling it stutter. The local-network gateway has trimmed history pages for the mobile layout since 0.1.7; the remote proxy did not, so the Tailscale channel received the full page. It now asks for 50 messages per page through the same rewrite, and `hasMore` keeps paging by 50 as the user scrolls up.
- **A Turn window wider than the page is narrowed with it.** `turnWindow.minMessages` must not exceed `maxMessages`, so trimming the page alone would have made the request invalid upstream (`gateway/bad-request`) — and could have produced exactly the empty-history symptom reported against the local-network channel. Both channels now clamp the window to the page size they ask for.

## 0.3.12

- **A 5.3 MB client module was downloaded and executed on every phone page.** Measured from the live 0.1.7 manifest, the mobile boot graph is 76 entries / 74 packages — 13.61 MB raw, 5.80 MB gzipped — and `@deepseek-ai/dsh-client-ui-settings-account` alone is 5,281,067 bytes raw / 3,775 KB gzipped: 65% of the transfer, and by far the largest single script a phone has to parse and execute while the first screen is already interactive. Nothing injects it (verified against the served graph itself: zero `require()` references outside its own body; the only cross-module mentions are plugin-inventory documentation strings), so the phone no longer receives it at all. The account and billing pages inside settings are the price; the desktop window keeps them.
- **Every combined boot request is now assembled and served by this plugin.** DSH 0.1.7 asks for the graph as one combined request per phase (`plugins/??a,b,c&rev=…`) and only answers the combination it built itself, so removing an entry from the manifest would still have shipped its bytes inside that request — which is why 0.3.11's removal of `dsh-desktop-next` never saved a download. The rewrite now points each batch at `/mobile-access/mobile-boot/<hash>.js`, assembled from the individual module sources with the same 8 MB per-module and 32 MB per-batch bounds, gzip, `ETag`/304 and per-request accounting as the rest of the mobile frontend. The url carries a hash of the pruned graph, so a pruned batch can never be confused with a stock one in any cache. The remote (Tailscale) channel serves those batches from the proxy's own store, because its document is rewritten there and the local-network gateway may be switched off.
- Batch assembly falls back to the upstream's own combined request when a module cannot be fetched, so a pruning failure costs speed rather than the page.

## 0.3.11

- **The dedicated mobile layout was substituted onto a layout generation it does not implement.** `mobile-layout.js` declares its own root slot children (`conversation`, `details`). DSH 0.1.7 replaced those with `main` (keyed), `rightbar` and `shell.leading`, so on that generation the substituted layout renders a page whose conversation is drawn into a slot nothing declares — no conversation at all. The rewrite now recognises the generation from the layout module's own dependency list and leaves the stock layout in place, where the `native-mobile.ts` surface adaptation carries the phone. Substitution and this plugin's own boot batch — redundant since that generation already serves one combined request per phase — are skipped together. This also removes a latent break on the local-network channel, which had been swapping in the unimplemented contract since 0.1.7.
- **A desktop-shell-only client module was being activated on phone pages.** DSH Desktop NEXT supplies `dsh-desktop-next` (1.1 MB raw, 628 KB gzipped) to every client graph. On the desktop window it draws the shell's own chrome; on a phone it is dead weight that also installs two `MutationObserver`s on `document.body` with `subtree: true`, one of them unthrottled. Measured on the phone channel, that competes directly with everything else for the main thread. The entry is now dropped from the served manifest, so the module stays inside the combined request but never activates; no other entry declares it as a dependency, so nothing else loses its placement. Covered by tests.

## 0.3.10

- **The mobile DOM layer re-ran itself on every animation frame.** `installNativeMobileSurface` drives its `sync()` pass from a `MutationObserver` over `document.body`, filtered to `class`/`style`/`disabled` — and DSH rewrites class tokens continuously while streaming, animating, or resizing the composer, so the observer fired on nearly every frame. `sync()` is not cheap: it scans the document for the layout roots and re-tags the center column, composer, settings dialog and sidebar. On a phone that saturated the main thread, so scrolling, typing and tapping all stuttered. The pass is now coalesced to at most one run per 150 ms, which is below the spacing at which a structure change is still visible. Covered by a test.
  - This became reachable when 0.3.6 fixed the layout probe: before that `sync()` returned early and the layer was effectively dormant, which is why the stutter appeared only then. The observer's filter is left as it was — `sync()` reads the details column's inline `grid-template-columns`, so dropping `style` would need that read replaced first.

## 0.3.9

- **A stopped Tailscale backend reported itself as a network problem.** With Tailscale installed but not connected, every `tailscale serve` invocation prints `Tailscale is stopped.` and exits non-zero. That wording matched none of the classifier's patterns, so the panel fell through to the generic `serve_failed`, whose guidance is "Check the network, then click Reconnect", and the diagnostic report repeated it — pointing the user at connectivity for a service they only had to switch on. A stopped backend now classifies as `tailscale_not_running`, with actionable guidance in both the control panel and the diagnostic report. Found on DSH Desktop NEXT once 0.3.8 fixed the `tailscale_missing` case: the CLI was reachable, the backend simply was not running. Covered by a test.

## 0.3.8

- **The desktop window was read as a phone page, so the sidebar launcher never existed.** The client decided "desktop or phone" with `isLoopbackHost(location.hostname)`, which only accepts `localhost`/`127.0.0.1`/`::1`. DSH Desktop serves its window from a private scheme — `dsh-app://app/` in DSH Desktop NEXT — so `hostname` is `app`, the test failed, and the plugin took the *phone* branch on the desktop: `installControl()` never ran, and with it the `sidebar.footer.action` registration that renders the "移动访问" entry. That entry was simply absent, which is why the remote switch could not be found.
  - The same misdetection explains a second symptom reported against 0.3.6: the phone surface was installed into the desktop window, so `NATIVE_MOBILE_STYLES` and the mobile DOM layer applied there, and `animateNavigation` replayed its 240ms view transition on every settings click — read as the settings UI flickering. `0.3.7` scoped a `:has()` rule in `CONTROL_STYLES` on the theory that it was the cause; that rule is never even applied on this origin (the phone branch injects `NATIVE_MOBILE_STYLES`, not `CONTROL_STYLES`), so it could not have been. The scoping is kept as hygiene, but the real fix is the origin test below.
  - Phone channels are always plain http(s) — the LAN gateway or the passthrough proxy — so the client now treats any other scheme as the desktop shell. Matching on the scheme rather than the literal `dsh-app:` keeps this working if the desktop renames its private origin. Relative requests from the desktop shell still reach the Host, because `dsh-app://app/` forwards everything outside `/`, `/assets/` and the manifest to the Host's loopback listener with its auth cookie attached.
- **Tailscale Serve failed with `tailscale_missing` on a machine where Tailscale was installed.** `bin()` returned the bare command `tailscale` and relied on `PATH`, but the Host process DSH Desktop launches runs with `/usr/bin:/bin:/usr/sbin:/sbin`, which omits `/usr/local/bin` and `/opt/homebrew/bin` — where macOS installs the CLI (a shim into `Tailscale.app`). The controller now resolves the first installed CLI among the known macOS, Linux and Windows locations, falling back to the bare name so a `PATH`-provided binary still works. Covered by a test.

## 0.3.7

- **The sidebar launcher's wrap rule reached every ancestor of the button.** `CONTROL_STYLES` scoped it as `div:has(.dsh-mobile-control__trigger)`, and `:has()` matches *any* div holding the trigger as a descendant — not just the immediate container. On DSH Desktop 2.0.10 that ancestor chain happened to be inert; on 2.0.15-next the sidebar was rebuilt (the footer slot is now a column flex box with its own height cap and scroller), so `flex-wrap: wrap` landed on unrelated ancestors and the layout jittered on every re-render — reported as the settings UI flickering on click. The selector now requires the trigger as a **direct child** (`div:has(> …)`), so only the launcher's own row is affected. This only became reachable once 0.3.6 let the plugin load on that runtime; the rule itself predates it.

## 0.3.6

- **Support DeepSeek Harness `0.1.7-rc.2`** (DSH Desktop 2.0.15-next) by declaring it in the `@deepseek-ai/*` peer ranges and in `SUPPORTED_DSH_VERSIONS`. Every frontend contract this plugin depends on was checked against that runtime before declaring it:
  - The boot manifest is still an assignment we can locate. `0.1.7` stopped inlining `window.__DSH_BOOT__ = <json>` and emits it through the webserver's index-injection table instead, which renders a `kind: "global"` row as `globalThis["__DSH_BOOT__"] = <json>` — a form `BOOT_ASSIGNMENT` already matched, because it was written with both spellings. The graph still carries `{rev, entries, batches}`, each batch still carries `{phase, url, rev, entries}` at the top level, and the phases are still `bootstrap`/`application`.
  - The layout module's dependency profile still matches by subset, so the new `@deepseek-ai/dsh-client-shortcuts` dependency is tolerated. `@deepseek-ai/dsh-client-runtime` no longer ships at all, so the runtime-v1 profile now matches nothing; it is kept because this release still supports the DSH versions that used it.
  - `_frame`/`_centerCol`, `_older` and `data-conversation-scroll` are unchanged, as are the `webServer` service (`register`, `host`, `port`), the connection trust contract (`isLoopback`, `ownsHost`), the settings trust read (`isLoopback ? "host" : "memory"`) and `commands.register`.
- **Why this was a hard outage rather than a warning.** DSH now validates a plugin's declared peers against the runtime and refuses to activate a plugin that does not cover it. With peers topping out at `0.1.2-rc.1`, the profile reported `Plugin dsh-mobile-tailscale@0.3.5 is incompatible with dsh 0.1.7-rc.2 … Exact-version exemption: not active` and left the entry inactive, so the whole plugin — host face included — was absent from the tree and mobile access disappeared entirely. Activation still uses the advisory path added in 0.3.3, so a *future* unverified Host version warns and continues; this release moves `0.1.7-rc.2` from unverified to verified instead of asking each machine for an exemption.

## 0.3.5

- **The mobile settings ordering had silently stopped running.** `orderAuthenticatedSettings` located this plugin's boot-manifest entry by the literal id `dsh-mobile`, but the entry id is the published package name (`dsh-mobile-tailscale`). The lookup found nothing and returned early, so the code that orders the authenticated settings module after this plugin never executed; DSH then resolved its settings to the in-memory backend on every mobile page, which surfaced as "settings are unavailable in this browser" and an unloadable model provider directory. The id is now derived from `package.json` (and the `tsdown` module-loader banner reads the same source), the stale requirement that the settings module depend on `connection` was dropped — DSH 0.1.2 moved its one-time `$host.isLoopback` read and declares only `@deepseek-ai/dsh-api-remotes` — and the test fixtures now match the real manifest shape, so a future drift fails a test instead of silently skipping the work.
- **The remote channel never rewrote its document.** `serveRewrittenDocument` gated the rewrite on a declared `Content-Length`, but DSH answers the application document with `Transfer-Encoding: chunked`, so every request skipped the rewrite. The body is now buffered to a bound instead, and a non-identity `Content-Encoding` skips the rewrite rather than feeding compressed bytes to a parser. A rewrite failure still serves the stock document, so the remote channel degrades instead of failing closed.
- **Opening the composer model menu closed it again.** The programmatic-focus guard meant to stop the iOS keyboard from popping on session open blurred *any* non-tapped text field. Drilling into the model list autofocuses its search field, so that blur fired the menu's own blur handler and dismissed the overlay; the sibling "推理等级" pane, which has no search field, was unaffected. The guard now covers only the composer editor it was written for.
- **A sidebar row's action menu was torn down by the row's own tap.** The portrait auto-collapse treated a tap on a row's ellipsis menu as selecting the row and collapsed the sidebar 240ms later, taking the just-opened menu with it. Only a row-body selection collapses the sidebar now, matching the guard the dedicated layout already had.
- **The "移动访问" entry shared a footer row with other plugins' entries** and was pushed past the sidebar edge, where the resize divider clipped it. The footer action row is allowed to wrap and this entry claims its own line, with its icon and label centered together.
- **The Android bridge's interactive actions cannot succeed.** `startPending` answers `files.pick` and `camera.capture` synchronously with `{ok:false, code:"pending"}`, and the page adapter rejects and forgets any non-`ok` reply, so the real asynchronous reply is dropped. Recorded here rather than changed: the fix needs a device to verify against.
- **Selecting a model on the phone did nothing.** The authenticated-transport trust was installed too late to survive DSH's own memoization. `@deepseek-ai/dsh-client-connection` builds its handle with `isLoopback: transport?.ownsHost === true || <loopback hostname>`; this plugin instead let `isLoopback` default to `false` on the phone and flipped it from the mobile client module's `apply()`. But `@deepseek-ai/dsh-api-gateway` snapshots `isLoopback` into cached `$host` facts keyed **only** on `home`, which is stable on the remote channel — so whichever module read `ctx.remote.$host` first froze `isLoopback: false` for the life of the page, and `dsh-client-ui-settings`, `dsh-client-ui-settings-general` and `dsh-api-session-controller` all read that cached value. The plugin now injects the pre-boot `window.__DSH_TRANSPORT__ = { ownsHost: true }` override that upstream ships, so the handle is born loopback-trusted on both channels, and `@deepseek-ai/dsh-api-gateway` is ordered after the mobile client on the remote-backed settings graph — both halves of the upstream 0.3.4 fix, which this fork had dropped while keeping only the settings edge. The injected statement deliberately does not throw when an override already exists: it shares a script block with the boot-manifest assignment, so throwing would blank the whole mobile page.

- **Tapping a model row on the phone sent no request at all.** A finger tap dispatches `mousedown`, whose default action moves focus out of the menu container — and that container closes itself from its own blur handler. It therefore unmounted between `mousedown` and `mouseup`, no `click` was ever dispatched, and the row's handler never ran: no request, no error, no toast, unchanged label. Only the deepest level broke because the model pane autofocuses its search field, while drilling from one root-pane cell to the other keeps focus *inside* the container and never blurs it — and a synthetic `click` (which dispatches no `mousedown`) always worked. `native-mobile.ts` now cancels just the `mousedown` default for a press on a menu item while focus is inside that item's menu, keeping the overlay mounted so the click gets through; cancelling `touchstart` or `pointerdown` instead would suppress the very click being delivered. Verified on the device against the emitted page, the RPC frames, and the host's own `session/modelCatalog` and `settings.yaml`.

- **The remote channel could reach the loopback-only administration surface.** The passthrough proxy rewrites `Host`/`Origin` to the loopback upstream, so anything it forwards arrives at the DSH WebServer looking exactly like a request from the local machine — and that surface is guarded by that loopback assumption alone. The LAN gateway already refuses its own admin prefix (`/api/mobile-access*`) on its own listener; the proxy did not, so any device on the tailnet could `POST /api/mobile-access/lan/pairing/open` and receive a complete pairing token and link, or list, revoke and clear the paired LAN devices — escalating tailnet membership to LAN-device trust. Reproduced against a live deployment before the fix (201 with a token, 200 with gateway state); now refused with `404 not_found` before the forward, on both the request and upgrade paths.
- **A disabled remote switch no longer clears `tailscale serve`.** `initialize()` ran `tailscale serve --https=443 off` whenever the persisted switch read disabled, and a fresh install persists exactly that — so booting DSH would tear down an unrelated 443 entry the user configured themselves, for a plugin that never owned it. A disabled switch means this plugin does not own `serve`, not that `serve` should be cleared; an explicit disable still clears the entry the plugin created.
- **A failed start no longer leaves the serve entry pointing at a closed proxy.** `runServe` registers the 443 entry before `resolveOrigin` reads the MagicDNS name back, so a failure after the registration left `serve` forwarding to a proxy the error path then closed — the phone saw connection-refused while the panel reported only a generic error. The error path now clears the entry it just created.

- **A port-443 conflict is reported as such.** The recovery path raises its own errors, and their wording ("…is occupied by another service") matched none of the message patterns the classifier looks for, so the panel showed the generic `serve_failed` and lost the actionable hint. Those failures now carry `serve_port_conflict` explicitly rather than relying on wording.
- **Release tooling that had drifted into doing nothing.** `scripts/check-mobile-release.mjs` defined its brand/store-icon and Android checks but never called them, so it exited 0 with no output while sitting inside `npm run verify`: every assertion it holds, including the pinned-certificate and network-security contracts, was unenforced. It now runs them. The release workflow's idempotence probe queried `npm view "dsh-mobile@$version"` — the upstream package — while this one is `dsh-mobile-tailscale`; because upstream publishes the same version numbers the probe matched and the publish step reported "already published" and skipped, so this package was never on npm while the GitHub release was still created. The name is now read from the packed manifest. The `files` whitelist also omitted three sourcemaps (`index.mjs.map`, `cli.js.map`, `index.d.mts.map`) that the shipped bundles reference.
- **Opening a project in the sidebar collapsed the sidebar.** The Workspace (project) header and a session row are both `div[role="treeitem"]`, but only the header carries `aria-expanded` — its click toggles the nested session list — while only a session row carries `aria-selected`, whose click opens the conversation. `selectsSidebarRow` decided purely on whether the tap resolved to a `button` ancestor, and a project title is a plain span, so the one gesture that opens the list was read as selecting a session: the portrait drawer closed 240ms later, over the list the user had just opened. A row that announces `aria-expanded` is now never a selection, and the dedicated layout's own drawer guard gained the matching `:not([aria-expanded])` so both layouts encode the same rule instead of only one. Covered by a regression test that fails without the guard.

## 0.3.3

- **An unverified Host version no longer aborts activation.** `assertSupportedDshVersion` threw from the first statement of `apply()`, so a version outside the verified set failed its loader entry, failed the whole plugin tree, and made DSH Desktop stop the harness and fall back to its safe-mode profile with **every** third-party plugin disabled. Activation now warns (`DSH_MOBILE_UNVERIFIED_DSH_VERSION`) and continues; the strict assert remains available for callers that want it.

- **Fix a 30-day timer overflow on the remote channel.** The pairing-free remote guest authorization used a 30-day (`2 592 000 000 ms`) expiry, and the derived abort/close delays were passed straight to `setTimeout`, which truncates any delay above `2^31 - 1 ms` (~24.85 days) to **1 ms**. Every remote request and WebSocket was therefore aborted immediately, logging `TimeoutOverflowWarning` and `upstream_unavailable (socket hang up)` in the harness log. Session-derived delays are now clamped to `MAX_TIMER_DELAY_MS`.

## 0.3.2 - 2026-08-29

- **Remote channel no longer hardcodes the web port.** Tailscale Serve now targets a plugin-owned loopback passthrough proxy that resolves the live upstream from the host `webServer` service per request (falling back to `DSH_WEB_URL`, then `upstreamOrigin`). The remote channel follows DSH Desktop's random per-launch web port automatically — no manual `tailscale serve` re-pointing after restarts.
- **Browser-trust fence bypass for remote.** The passthrough proxy rewrites `Host`/`Origin` to the upstream origin (the same proven pattern as the LAN gateway) and injects the upstream session cookie, so phone `/api` calls no longer hit the DSH browser-trust fence 403 while staying pairing-free.
- **Automatic stale serve-config recovery.** Starting Serve now detects a port-443 occupancy (`already serving TCP` etc.), clears it when 443 is the only serve entry, and retries once; a conflict with other serve entries surfaces a dedicated `serve_port_conflict` error instead of the generic `serve_failed`.
- **LAN gateway upstream follows the live instance too.** Both LAN and remote paths resolve the upstream through the webServer service, so neither depends on a fixed port being occupied by a particular instance.
- **Transparent WebSocket passthrough.** The proxy forwards every upgrade request (any path, query preserved) instead of whitelisting three core channels, so plugin channels such as `/sidebar/ws/agent-opens` and `/sidebar/ws/agent-terminals` keep working remotely. Upgrade failures now log a diagnostic line to the harness log instead of being masked as an EOF.
- **Pairing-free mobile-frontend assets on the remote path.** The DSH WebServer mirrors the LAN gateway's mobile metadata, custom css/js, mobile layout module and extension registry (without the LAN device-pairing requirement), so the phone's mobile UI features load over the Tailscale Serve channel too.
